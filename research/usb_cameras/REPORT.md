# Low-cost USB (UVC) cameras: MJPEG, timing, bandwidth, naming — Report

Status as of 2026-10-28: **in progress.** Goals 1–4 are measured on Windows only; goal 5 (cross-platform) is not written, and no Linux or macOS hardware run has happened. Raw material: [`results/windows/Gerald/`](results/windows/Gerald/) (2000+ files), with progress and errata in [PROGRESS.md](PROGRESS.md) and the overnight re-check in [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md).

Terms used below: **UVC** = USB Video Class, the standard webcam protocol. **MJPEG** = each frame sent as a separate JPEG. **MF** = Windows Media Foundation. **DShow** = DirectShow. **PTS/SCR** = timestamps in each UVC payload header, counted on the camera's own clock (PTS = presentation time stamp; SCR = source clock reference, which pairs the camera clock with the USB frame counter, called SOF). **QPC** = the Windows high-resolution host clock. **Alt setting ("alt")** = one of the fixed isochronous (reserved-bandwidth) slot sizes a camera offers; the host must reserve the whole slot whatever the camera actually sends. **WinUSB** = Microsoft's generic USB driver, which must replace the normal camera driver (`usbvideo.sys`) before libusb/libuvc can talk to a camera on Windows.

## Executive summary

The study asked how skellycam could get better data out of cheap UVC webcams: (1) the camera's own JPEG bytes without re-encoding, (2) accurate per-frame capture times, (3) control over USB bandwidth so more cameras fit on one bus, (4) stable camera identities, and (5) a cross-platform design. All measurements come from one Windows 11 machine ("Gerald", i7-14700K) with a Logitech C922, a Logitech C930e and a generic "USB Camera" 4C4A:4A55, measured on 2026-10-25 and re-run and adversarially re-verified unattended on the night of 2026-10-27/28; a Razer Kiyo Pro was in the 10-25 runs but was excluded from the re-run as faulty.

Answers so far, on Windows: **(1)** Media Foundation's source reader with the native MJPG type, and PyAV/FFmpeg DirectShow with `vcodec=mjpeg`, both return the camera's own JPEG bytes at full frame rate for about 1–2% of one CPU core, while OpenCV (skellycam's current capture path) always decodes, at 25–156% of a core. **(2)** Windows OS timestamps and arrival times sit on a 16 ms grid (about 4.4–5 ms error against a screen-flash ground truth); the camera's own UVC PTS, exposed through MF after a one-time admin registry setting, scores about 0.5 ms, which is the floor of the test method, so the true accuracy is at most that and not yet known. **(3)** Every camera requests its largest bandwidth slot and Windows grants it, so effectively one MJPEG camera per USB 2.0 link; the only way found to use smaller slots is to swap the driver to WinUSB and pick the alt in the app (libusb), which ran the C930e at 30 fps in 800 B (720p) or 1600 B (1080p) slots on a static scene. **(4)** Name cameras by USB serial when present and unique, otherwise by physical port path; indices, MF symbolic links and serial-less ContainerIds all changed during the study.

For skellycam this means: switch MJPEG capture on Windows away from OpenCV to MF (or PyAV DirectShow) passthrough, timestamp from UVC PTS where the registry value is set, key cameras by serial/port, and treat driver-swapped libusb capture as a promising but unvalidated route to more cameras per bus. Linux and macOS are not measured at all yet.

## Key findings

Confidence labels: **measured** (result file on Gerald supports it and the overnight re-run reconfirmed it), **provisional** (measured once, weakened by the re-run verifier, or needing a re-check), **inferred** (from source code or documentation, not run).

### Goal 1: native MJPEG

1. **MF IMFSourceReader with the native MJPG type and converters disabled returns the camera's own JPEG bytes.** 100% valid JPEG on all three cameras at 1280x720@30 and 1920x1080@30; C922 30.00 fps, C930e 30.05 fps, generic 25.76–25.78 fps; 0.7–2.2% of one core for the capture process (Frame Server CPU excluded: it needs elevation). **Measured.** [mjpeg/RESULTS.md](mjpeg/RESULTS.md), [table.md](results/windows/Gerald/mjpeg_rerun_20261027/table.md)
2. **PyAV 19.0.2 / FFmpeg DirectShow with `vcodec=mjpeg` (demux only) returns byte-identical JPEG headers to MF** (full SOI–SOS header SHA-1 matches, per camera and mode), so neither path re-encodes. 0.9–1.6% of one core for one camera. **Measured.** [mjpeg/RESULTS.md](mjpeg/RESULTS.md) finding 2. Caveat: on 10-25 the Kiyo Pro fell back to raw YUY2 under PyAV DirectShow (not re-tested). [prior_art/SURVEY.md](prior_art/SURVEY.md)
3. **OpenCV 4.12 never returns JPEG bytes.** CAP_DSHOW decodes to BGR at 24.6–28.3% of one core at 720p and 37–40% at 1080p; CAP_MSMF costs 46–54% at 720p and 143–156% at 1080p, and takes 39–41 s to open each Logitech camera (3.4–3.7 s for the generic). The earlier "MSMF gives 0 frames" result was a harness bug (30 s open wait). **Measured.** [mjpeg/RESULTS.md](mjpeg/RESULTS.md) finding 6
4. **WinRT MediaFrameReader with the MJPG subtype delivers nothing** (every acquire fails with E_INVALIDARG, all cameras and variants); without a subtype it delivers decoded NV12. **Measured.** [mjpeg/RESULTS.md](mjpeg/RESULTS.md) finding 5
5. **Other native-JPEG paths on Windows:** nokhwa (Rust, MSMF backend) 593/593, 588/588 and 515/515 frames native; GStreamer `mfvideosrc` and `ksvideosrc`; SDL3 3.4.18 (10-25 only, 4/4 cameras). pygrabber and openpnp-capture force RGB24. **Measured.** [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md), [prior_art/SURVEY.md](prior_art/SURVEY.md)
6. **The generic 4C4A:4A55 camera delivers about 25.7 fps when 30 is requested**, on every path and both days, at fixed manual exposure (so not light-limited). OpenCV MSMF reports 30 fps for it by repeating frames (48 of ~300 duplicated). Its 1080p frames fail a strict libjpeg-turbo decode on every frame (387–1195 extra bytes before the end marker) though lenient decoders accept them. **Measured.** [mjpeg/RESULTS.md](mjpeg/RESULTS.md) finding 3, [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md) goal 3 table

### Goal 2: capture timing

Ground truth is a full-screen black/white flash sequence on a 59.95 Hz monitor, logged against QPC, filmed by the cameras ([timing/VERIFY_method.md](timing/VERIFY_method.md)). Errors are standard deviations after removing one constant offset per source unless marked MAD (median absolute deviation).

7. **Windows OS timestamps and host arrival times are quantized in ~16 ms steps.** On the C922, MF sample time scored 4.40–4.52 ms and host arrival 4.59–4.98 ms against the flash ground truth in the six valid exposure −7 runs of 10-27/28 (16/√12 = 4.62 ms is what uniform 16 ms quantization predicts). The DirectShow device sample time is synthesized (constant intervals, +141 ms/s drift on the generic camera). `timeBeginPeriod(1)` does not remove the quantization but did reduce arrival-phase jitter from 0.3–0.5 to 0.05–0.08 ms. **Measured.** [compact_table_all_runs.txt](results/windows/Gerald/timing/rerun_20261027/compact_table_all_runs.txt), [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md) prior-art table
8. **Raw UVC PTS/SCR can be read through MF** once the `MetadataBufferSizeInKB0` registry value is set per camera interface (admin, once, then a replug): every C922/C930e frame then carries the UVC header (292/292 and 287/287 frames); the generic camera, not set, has none. **Measured.** [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md) goal 2 table. Revert script: `timing/scripts/revert_uvc_metadata.ps1`.
9. **C922 UVC PTS scores 0.47–0.68 ms against the flash ground truth (exposure −7 runs; 0.40 ms in one exposure −9 run), but that is the method's floor, not the PTS accuracy.** A pure frame-counter model with no device timestamp scores the same, and fitting PTS directly to the ground truth still leaves 0.49–0.59 ms. So the result is an upper bound of about 0.5 ms. The best scores also use a whole-run (non-causal) fit; causal versions scored 0.59–1.13 ms (C922) and 0.61–3.6 ms (C930e) depending on start-up handling. **Measured (as an upper bound).** [compact_table_all_runs.txt](results/windows/Gerald/timing/rerun_20261027/compact_table_all_runs.txt), [timing/VERIFY_method.md](timing/VERIFY_method.md)
10. **C930e PTS is a synthetic counter, and the camera has two frame-period modes (998,400 vs ~997,230 camera-clock ticks per frame) with an unknown trigger.** The once-reported "PTS steps by two periods every ~24 s" appeared in only 1 of 6 flash runs on 10-27/28; its 8–12 ms OS-timestamp error on 10-25 dropped to 4.7 ms in the one valid run of the other mode. Use its SCR/STC, not PTS. **Provisional** (mechanism untested). [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md) goal 2 table
11. **C930e manual exposure set through MF before streaming is not reliably applied** (1 of 5 valid −7 runs integrated for the requested time; it reads back −5 after capture), so earlier C930e flash results that assumed a known exposure are suspect. On libusb, exposure set only before stream commit was also not applied (step rise ~32 ms instead of ~12 ms). **Measured.** [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md)
12. **Rolling shutter spans about 30–31 ms of a 33 ms frame** (30.1–31.5 ms per frame height on the C922), so a marker's capture time depends on its image row. C922 PTS sits near the end of exposure, not the start (offset ≈ −1.14 × exposure change). **Measured** (rolling shutter); **provisional** (PTS position). [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md)
13. **On libusb/WinUSB (phase 2, C930e only), the SCR-derived frame time and the host's first-payload callback time (back-dated by packet index) agree closely:** median offset +0.31 to +0.33 ms, robust (MAD-based) sigma 46–58 µs per run, plain std 55–67 µs (214 µs in the 8-packets-per-transfer run); the phase-2 verifier's four fresh runs reproduced the median (+0.32 to +0.35 ms) and robust sigma (52–66 µs) but not the plain std (127–223 µs) ([phase2_timing_verify/](results/windows/Gerald/phase2_timing_verify/)). Against the flash ground truth, SCR scored 0.41–0.74 ms MAD and back-dated arrival 0.39–0.78 ms MAD, the same as a frame-counter model (0.36–0.73 ms), i.e. again the method floor. libusb host arrival scored 1.0–1.7 ms MAD, versus 5.8–6.1 ms MAD for the C922's MF OS timestamps in the same runs. **Measured** (agreement); **provisional** (the SCR→QPC basis, see finding 14). [summary_runs2-6.json](results/windows/Gerald/phase2_libusb_scr_timing/summary_runs2-6.json)
14. **The xHCI frame-number/QPC IOCTL that maps the USB frame counter to QPC is only exact for ~2–3.5 s after tracking starts.** Over 20 s the mapping shifted by up to +53 µs on one controller and −641 µs on the other, and the returned QPC was later than the QPC read after the call returned in 41/396 and 208/396 samples (camera-less verifier run, 10-28). The phase-2 claim that SCR→QPC mapping is "causal with residual 0" came from a ~2 s window and is weakened; the agreement above needs re-checking over longer runs. **Measured** (the drift); its effect on phase-2 timing is **unknown**. [README.txt](results/windows/Gerald/uvc_capture_frame_qpc_only/20261028T0353Z_verifier_rerun20261027_20s/README.txt)
15. **Cross-camera sync is not established.** With a fixed region of interest, the C930e (libusb SCR) minus C922 (MF PTS) offset varied with a standard deviation of 0.54–0.79 ms across 5 runs, comparable to the ground-truth floor. An earlier "offsets agree to 0.02 ms" was a search-grid artefact. **Provisional.** [summary_runs2-6.json](results/windows/Gerald/phase2_libusb_scr_timing/summary_runs2-6.json), [timing/VERIFY_method.md](timing/VERIFY_method.md) section 6

### Goal 3: USB bandwidth

16. **Each camera asks for its largest alt and `usbvideo.sys` grants it.** The C930e requests 3072 B per 125 µs microframe at 720p and 1080p MJPEG regardless of the quality (`wCompQuality` 2–61) or payload size the host proposes; at 480p it requests alt 10 (2688 B). Max-alt reservations are 24.48 / 24.576 / 24.552 MB/s (C922 / C930e / generic), about 62% of the USB 2.0 periodic budget each, so two such cameras cannot share one USB 2.0 link. The generic camera has a single alt (3069 B), so no driver can shrink it. **Measured.** [phase2_bw_alt/summary.json](results/windows/Gerald/phase2_bw_alt/summary.json), [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md)
17. **Admission control is enforced by the USB controller, and a USB 2.0 budget model predicts it.** Next to the streaming generic camera on the same Genesys hub, the C930e started at alt 8 and was refused at alt 9 (5/5 each on 10-27/28); the "80% of a microframe" model matched 26/26 combinations. In an earlier window, when an audio device on the same root-port link probably held isochronous pipes (seen in a snapshot taken just after; the phase-2 verifier rated this cause likely, not verified), alt 6 passed and alt 7 and alt 8 were refused. With no start stagger, which camera loses is a race. Cameras on different root ports did not compete. **Measured.** [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md) goal 3 table, [coexist_gen_first.json](results/windows/Gerald/phase2_bw_alt/coexist_gen_first.json), [coexist_run2_alt7_alt4_reverse_order.json](results/windows/Gerald/phase2_bw_alt/coexist_run2_alt7_alt4_reverse_order.json), [coexist_run4_audio_idle_alt7-9.json](results/windows/Gerald/phase2_bw_alt/coexist_run4_audio_idle_alt7-9.json)
18. **An app-chosen alt (libuvc/libusb on WinUSB) works, on the C930e.** Static scene, 20 s per alt: 720p held 30 fps with zero skipped frames from alt 5 (800 B) up; 1080p from alt 8 (1600 B; alt 7 gave 30.04 fps with 1 skipped frame); 480p from alt 3 (alt 2 had 1 skip). With full-contrast noise on screen, 720p held 30 fps at alt 6, but 1080p at alt 8 dropped to 19.2 fps. With the generic camera streaming via MF on the same hub, the C930e streamed 30 fps at alts 4–8. Delivered fps followed 30 / ceil(frame size / slot capacity) in 47 of 48 runs. **Measured, one camera, one machine.** [phase2_bw_alt/summary.json](results/windows/Gerald/phase2_bw_alt/summary.json), [coexist_run3_alt4_alt5_retest.json](results/windows/Gerald/phase2_bw_alt/coexist_run3_alt4_alt5_retest.json)
19. **Too small a slot drops whole frames rather than corrupting them**: 0 corrupt frames under strict libjpeg-turbo decoding in 15,821 (Rust runs) + 2,135 (verifier runs). Pillow cannot detect truncated frames from this camera, so a strict check matters. **But a refused start is followed by a zero-frame start** (5 of 5 cases: 2 in the phase-2 coexistence runs and 3 in the verifier's runs; the start after that works), and the first frame after a zero-frame run was once truncated (no end marker, error bit set). **Measured.** [zero_frame_after_refused_start.json](results/windows/Gerald/phase2_bw_alt_verify/zero_frame_after_refused_start.json), [strict_jpeg_check_sweep.json](results/windows/Gerald/phase2_bw_alt_verify/strict_jpeg_check_sweep.json), [PROGRESS.md](PROGRESS.md)
20. **The C922 at MJPEG 1080p@5 fps delivers 5.01, 15.76 or 30.0 fps at the same alt 5**, run to run, with only ~1.17x slot headroom at 30 fps. **Measured** (non-determinism); cause unknown. [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md)
21. **On Linux, `UVC_QUIRK_FIX_BANDWIDTH` (quirks=128) applies only to uncompressed formats in mainline uvcvideo** (same condition from v3.2 to current master). This conflicts with the maintainer's experience that it helps MJPEG. **Inferred** (source reading), untested. [prior_art/SURVEY.md](prior_art/SURVEY.md)

### Goal 4: naming

22. **Use the USB serial if present and unique, else the physical port path.** Only the C922 has a serial (B76395EF); the other three get Windows instance IDs built from the parent hub and port. The key scheme is in [naming/camera_identity.py](naming/camera_identity.py); listing takes 0.095–0.102 s in-process, without admin. **Measured.** [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md) goal 4 table, [check_claims.json](results/windows/Gerald/naming_rerun_20261027/check_claims.json) (46/46 checks)
23. **Indices, MF/DirectShow paths and serial-less ContainerIds are not stable.** After the C930e's WinUSB install/rollback (same port) its instance ID, KS/MF/DShow/FFmpeg paths, ContainerId and MF/DShow indices all changed (MF 7→6, DShow 7→2), while its composite ID, location path and the port-based key did not. Two unattributed reboots changed only USB addresses. **Measured** (opportunistic; the controlled reboot / replug / port-move test has not run). [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md)
24. **All descriptors (serial, alt settings, formats, clock frequency) are readable without admin** via the parent hub's IOCTL, byte-identical across runs. **Measured.** [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md)

### Libraries and drivers

25. **libuvc** builds on Windows (MSVC) with 3 shims plus patch 0001 (exposes PTS/SCR and allows an alt override): [libusb/patches/](libusb/patches/). **pyuvc 1.0.8 from PyPI crashes** (access violation) on Windows; a locally patched build (1.0.8.post0+winusbfix) streamed. A **pure-Python libusb1 streamer** works at ~4–8% of one core. **Rust `uvc_iso`** on libusb streamed every run (0.6–2.9% of one core); on the `rawusb` 0.1.7 backend it was intermittent (0, 15 and 15 fps in three alt-4 runs). **nusb** has no isochronous support (PR #233 closed unmerged; its fork accepted only 1 queued transfer). **Measured.** [PROGRESS.md](PROGRESS.md), [phase2_rust_uvc_iso_summary.json](results/windows/Gerald/phase2_rust_uvc_iso/phase2_rust_uvc_iso_summary.json), [phase2_python_libusb/summary.json](results/windows/Gerald/phase2_python_libusb/summary.json)
26. **The WinUSB driver swap costs:** one UAC prompt plus a replug; the camera disappears from normal apps and its microphone vanishes; rollback (`pnputil /remove-device /subtree` + `/scan-devices`) gives the functions new instance IDs (`&0&`→`&1&`) and re-requires the metadata registry value. **Measured** (C930e only). [rollback_result.json](results/windows/Gerald/winusb_install/rollback_result.json), [PROGRESS.md](PROGRESS.md)

**Winner and caveats.** For skellycam on Windows today, MF native-MJPG passthrough is the clear winner (PyAV DirectShow if staying in Python), with UVC PTS from MF metadata as the timestamp. The libusb route is the only one that controls bandwidth and gives the cleanest timing, but it requires a driver swap that hides the camera from every other app, was tested on one camera model only, and its SCR→QPC basis needs re-checking. All CPU figures are capture-process only, single 10 s windows, and 1.3–2.3x higher on 10-27/28 than on 10-25 for unexplained reasons; the ranking did not change.

## Areas of interest

- **The 16 ms quantization sits below Media Foundation** (it also appears on the kernel-streaming path), so no Windows capture API can avoid it; only the camera's own timestamps can. Hypothesis, unverified: frames complete only at isochronous transfer-completion boundaries. [prior_art/SURVEY.md](prior_art/SURVEY.md)
- **MF arrival-minus-sample latency is bimodal** (~0.3–1 ms or ~16 ms on the Logitech cameras) with a ~12-frame beat whose phase differs per run; report both modes, never a median. [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md)
- **Frame size depends on autofocus and scene**, not just resolution: C930e 720p frames ranged ~117–180 kB on a static scene and ~240 kB with screen noise, which sets the minimum safe alt. [phase2_bw_alt/summary.json](results/windows/Gerald/phase2_bw_alt/summary.json)
- **usbvideo over-reserves massively for MJPEG** (reserved/used ratio ~6x for the C930e at 720p30 and ~50–70x for the generic camera), and the ratios moved between runs within noise. [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md)
- **Unexplained camera behaviour:** the generic camera re-arrived twice overnight with nothing logged; the C930e has two frame-period modes; the C922 1080p@5 rate is non-deterministic. [PROGRESS.md](PROGRESS.md)
- **Enumeration touches cameras.** libusb enumeration sends hub requests (including GET_DESCRIPTOR) to every device, and GStreamer ksvideosrc, SDL3, openpnp and libuvc's listing open every camera. A capture library that must avoid a faulty camera needs filtered MF/DirectShow enumeration. [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md) "Kiyo contact"
- **Kiyo Pro:** stops answering control requests a few minutes after each plug-in (every API then fails with 0x8007001F); device/firmware fault. [PROGRESS.md](PROGRESS.md)
- **Prior art:** librealsense reads UVC PTS/SCR through the same MF metadata path; Pupil Labs pyuvc maps PTS to host time and exposes `bandwidth_factor`; libcamera builds port-based camera IDs on Linux; no surveyed library controls bandwidth through MF, DirectShow, KS or AVFoundation. **Inferred** (docs and source). [prior_art/SURVEY.md](prior_art/SURVEY.md)

## Limitations and caveats

- **One machine, one OS.** Every measurement is from Gerald (Windows 11 build 26300, Intel xHCI controllers, i7-14700K). No Linux or macOS hardware run exists; those harnesses only passed static checks and fake-sysfs/fake-ioreg plumbing tests (`results/linux/` is WSL2 or Docker, not real hardware).
- **Few cameras, small samples.** Three in-scope cameras (C922, C930e, generic 4C4A:4A55); the Kiyo Pro was excluded from the re-run. Most cells are a single 10 s or 20–30 s run. WinUSB/libusb results are C930e only; the C922 and generic on WinUSB (phase 3) have not run. No link has carried three or more cameras.
- **Conditions.** The 10-27/28 re-run was unattended in a dark room (C922 luma ~17) with manual exposure 2^-7 s; the generic camera was never measured in a bright scene. Six agents shared the machine (machine CPU mostly 2–21%, peaks ~60%). One of ten flash runs was invalid (display glitches).
- **Timing method floor.** The flash method cannot resolve below ~0.5 ms and its ground-truth offset varies by ~35 ms across image blocks (rolling shutter plus display scan-out), so sub-millisecond claims are upper bounds and per-camera absolute offsets are not measured. Generic-camera timing accuracy is unmeasured (an earlier 1.7–1.9 ms figure was circular).
- **Known errors in earlier write-ups.** The Claude Docs report ([USB camera report](https://claude.ai/artifact/WrpwyyMF7yU1amEB9pQYgE)) has goals 2–4 written on 10-25 data; local results contradict it on: the C930e PTS "jumps every ~24 s" (now 1 of 6 runs, mode-dependent) and its 8–12 ms OS error; the xHCI IOCTL "causal, 2.4–8 µs residual" (holds only ~2–3.5 s); MF/DShow indices "unchanged" (they changed); naming listing time "0.29–0.37 s" (that includes `uv` start-up; in-process 0.095–0.102 s); and it does not mention that C930e MF manual exposure is unreliable. Its 1080p "smallest alt 8" is right for zero skipped frames. Goal 1, goal 5, the summary and the comparison matrix are still empty in the doc.
- **Other corrected claims:** OpenCV MSMF "0 frames" (harness bug), OpenCV DSHOW "10 fps YUY2" (property-order dependent), rawusb "sees only root hubs" (patched crate lists all cameras), C930e DirectShow drift "−4.5 ms/s" (outlier; about −1.5 to −1.8 ms/s). [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md)
- **Machine state left changed:** cameras left at manual exposure −7, WB 4500 K; metadata registry values set on three cameras. [PROGRESS.md](PROGRESS.md)

## Proposed further investigation

1. **Re-check libusb SCR→QPC timing over 30–60 s runs** with the xHCI IOCTL re-sampled periodically (or re-anchored), and compare against back-dated arrival. Decides whether WinUSB capture really gives sub-millisecond, causal per-frame times.
2. **WinUSB phase 3: C922 and generic on WinUSB, then 3+ cameras on one USB 2.0 link at forced alts**, with strict JPEG decode. Decides whether the "3–6 cameras per link" model estimate holds and whether driver swapping is worth its cost. Needs one announced UAC prompt and replugs (scripts drafted, unverified: `libusb/winusb/`).
3. **Run the Linux drafts on real hardware**, including uvcvideo `quirks=128` with MJPEG vs YUYV, the V4L2 metadata node for PTS/SCR, and libuvc via a udev rule. Decides the Linux architecture and settles the FIX_BANDWIDTH conflict.
4. **Run the macOS AVFoundation native-format probe** (`videoSettings` empty) to see whether MJPEG bytes are reachable at all on macOS. Decides whether macOS needs decode-and-re-encode or a different path.
5. **Controlled naming tests** (reboot, same-port replug, port move, especially the serial C922) with `naming/win_stability_workflow.ps1`. Decides whether the serial/port key is safe to persist in skellycam configs.
6. **Isolate the C930e period modes and exposure handling**: re-apply exposure after stream start, with LogiTune's updater stopped. Decides whether the C930e can be timestamped from PTS at all.
7. **Independent sync ground truth** (an LED with no display scan-out, both cameras imaging it on the same rows, repeated runs). Decides real cross-camera sync accuracy, which the flash method cannot.
8. **Tests the verifiers flagged as missed but runnable unattended** (CPU repeat runs with CPU frequency logged, C922 720p60, MF-NV12 at 1080p, unpatched rawusb, Docker libuvc build). Listed in [RERUN_20261027.md](results/windows/Gerald/RERUN_20261027.md).
9. **Write the missing report sections** (goal 1, goal 5, summary, comparison matrix) into the Claude Doc and correct goals 2–4 as listed above.
