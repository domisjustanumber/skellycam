## 2. Start command

**Dom, 2026-11-09: no fresh Kiyo replug before a run.** The ~210 min wedge is a theory, not a proven trigger (run 3
on 11-06/07 polled the Kiyo for 305 min with no wedge). Dom suspects a collision: several processes reaching the
Kiyo at the same time. Start as found. If the Kiyo wedges, the run records when and what was running, gates it,
re-probes it at each later test and carries on. A start at 12:33 on 2026-11-09 was stopped after about a minute at
Dom's request (`results/windows/Gerald/suite_20261109T173335Z`, marked aborted). The full run is scheduled for 23:00
that day from a fresh session: [HANDOFF_FULL_RUN_20261109.md](HANDOFF_FULL_RUN_20261109.md).

```text
cd C:\Users\Dom\GitHub\freemocap\skellycam
uv run --python 3.12 --script research/usb_cameras/suite/windows/run_suite.py --plan
uv run --python 3.12 --script research/usb_cameras/suite/windows/run_suite.py --cyc-profile reliability --reliability-cycles 400 --min-fps 30 --min-height 720 --max-height 720
```

- The first line is a pre-flight. It only enumerates cameras and opens none. Check two things in its camera list:
  the Kiyo is `speed SS`. (Its plug-in age is recorded but no longer matters; see the note above.) Exit code 3 is
  the planner's age-based order check; the live run never applies it.
- In the second line, every flag is already the full-run default; they are written out so the log records them.
  `--quick` would switch to the quick profile, so do not add it.
- **Do not wrap `run_suite.py` in camlock.** The runner wraps every camera command in
  `tools/camlock.py`, with the timeout on the child (`ctx.camcmd`). Wrapping the whole runner would make each inner
  camlock wait on the outer lock until it times out. Camlock also keeps other agents' camera work out for the whole run.
- Ctrl-C stops cleanly. W-KIYO is written, and W-CYC keeps `W-CYC.partial.json` after every variant.
  To finish later: `--only W-CYC` (or `--skip` the tests already done).

## 3. Preconditions

- **Kiyo at SuperSpeed** (no fresh replug needed; Dom 2026-11-09). At start-up, discovery reads each camera's
  negotiated speed and bcdUSB from the hub driver's cached state (no device request). It also reads LastArrivalDate,
  which gives the plug-in age. Both go into `run_suite.json` `usb_link_check` and the "USB link at run start" table in
  `summary.md`. A Kiyo that is not at SuperSpeed gets a loud warning and a W-ENV flag. **The run does not abort**,
  so read the pre-flight. Expected: bcdUSB 0320, Thunderbolt xHCI / Genesys hub, port `.../USBROOT(0)/4.4`.
- **No other app using the cameras.** Close the camera app, Teams, Zoom, OBS and NVIDIA Broadcast. Close LogiTune
  and Razer Synapse if possible: they can write controls. If they stay open, W-ENV records them
  ("Logitech software running" / "Razer software running"), and the report should say so.
- **Gerald must not sleep** for about 8 h. The suite never changes the power plan. Leave all four cameras where they are.
- **Scene for W-CTRL-EFFECT, W-AUTO and W-OCV-CTRL** (from about 43 min to 2h18m):
  - Every camera sees a static, textured target in the centre half of the frame, within its focus range.
  - Light is steady, with no daylight drift and nobody walking through the view.
  - Mid-grey brightness: a dark (luma < 30) or bright (> 225) baseline rates "inconclusive", not "no".
  - In smoke 2 the Kiyo's AF was inconclusive: its baseline sharpness kept moving (CV 0.85-1.17), so it was hunting.
    Give it a close, high-contrast target.
  - The C922 started smoke 2 dark under AE (luma 42-47, against 132-141 earlier). Look at a C922 frame before
    starting. If it is dark, cycle its AE in any app, then close that app.
- **Tier 0 only.** No test writes, reads into a rating, or depends on the `MetadataBufferSizeInKB0` value. W-ENV only
  records whether it is present. Note: it is **not** in place now. An elevated step removed it on 2026-11-09 at 08:49
  (`results/windows/Gerald/metadata_revert_20261109/revert.log`, removed=26), and smoke 2 read it absent on every
  current instance. Either way the run is valid.
- wincam 1.2 is already built at `native/build/wincam.exe` (section 6). No rebuild is needed.

## 5. What the smoke tests proved, and what is still unproven

Proved on hardware (about 50 min of camera time; nothing wedged or re-arrived; controls restored):
- Smoke 1 ran W-ENV, W-TOPO, W-RAW, W-TS, W-PYMF, W-AUTO, W-OCV-CTRL, W-PYAV-LIST and W-CYC (quick), plus a wincam 1.2
  self-test. Result: 21 checks passed, 9 failed. All 9 were harness bugs, fixed offline in the same round: the OpenCV
  MSMF format sets had no bound, W-OCV-CTRL stopped after a hang, OpenCV get() was trusted, W-TS counted false drops on
  the ffmpeg wall clock, W-AUTO used the wrong reference window, W-CYC judged fps on short cycles, plus first-failure
  classification, and the pymf fps and Wilson labels.
- Smoke 2 re-ran W-ENV, W-TS, W-PYMF, W-AUTO, W-OCV-CTRL and W-CYC after the fixes: 14/14 passed, no device faults.
- Ratings seen:
  - pymf matches wincam on all 4 cameras.
  - Kiyo raw (W-RAW): MF, PyAV and ffmpeg give yes. The other cameras have no raw mode in scope.
  - PyAV listing "touches but harmless" while healthy.
  - W-AUTO AE is yes on every camera.

Still unproven:
- Not run since today's changes: W-POLICY, W-ID, W-FMT, W-FMT-NOGRAB, W-CTRL-LIST, W-MJPEG, W-CTRL-EFFECT and W-MULTI.
  They ran on 11-06 with wincam 1.1, but the harness-bug fixes since then have not met a camera.
- Not run at all: W-CYC-KIYO as its own test, the W-KIYO background poller (smoke used `--only`), the full
  reliability profile, and a full 7 h run.
- W-RAW and W-PYAV-LIST were not re-run after the smoke-1 fixes.
- W-PYAV-LIST has never met a wedged Kiyo.
- W-PYMF does not cover these, and its overall verdict is capped at partial:
  - one pymf process streaming all cameras;
  - 60 fps;
  - control sets while streaming;
  - in-use detection.

## 6. Building wincam from the repo

The Windows SDK headers and libs were removed from Gerald on 2026-11-07. `native\build.bat` handles this:
1. It calls vcvars64 (VS 2022 Build Tools are enough).
2. If `windows.h` is missing, it downloads Microsoft.Windows.SDK.CPP and .x64 10.0.22621.3233 from nuget.org into
   `native\build\sdk\` (git-ignored, SHA-256 checked, re-used on later builds).
3. It compiles with `/W4 /permissive- /std:c++17 /utf-8`.

Overrides: `WINCAM_SDK_DIR` and `WINCAM_FORCE_NUGET_SDK=1`. `native\build\sdk` is seeded (about 814 MB). Delete it
to force a fresh download of about 200 MB. `wincam.exe --version` prints `wincam 1.2 (2026-11-08)`, and 1.1 is kept as
`build\wincam_1.1_20261106.exe`. Details are in [native/README.md](native/README.md).

## Known risks

  11-06 both wedges came with other holders: LogiTuneAgent and RazerAppEngine held the Kiyo, and R2's onset was inside
  W-MULTI's staggered DS opens. A wedge is a recorded result: the gate skips the Kiyo's streaming work while it is
  faulted, re-probes it at each later test, and un-gates it if it answers. Only a replug has ever recovered it.
- The run_suite.py docstring (step 3) still lists W-CYC-KIYO before W-CTRL-EFFECT. The `TESTS` list and `--plan`
  are correct.
- The C930e's manual gain readback drifts while streaming (5 -> 6 or 3). This is camera behaviour, not a restore bug.
