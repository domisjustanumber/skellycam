# C++ comparison stage: would porting SkellyCam hot paths to C++ raise throughput?

Pinned SkellyCam commit: `23ccbf208e43879bfc74fc01049e5af2a623933d` (the checkout was at this HEAD; no source file was modified).
Every C++ program here has a Python twin that runs the **same workload with the same config, frame counts, process
topology and timing rules**, and the Python side exercises the **real SkellyCam classes** where SkellyCam behaviour is
measured (`CameraGroupSharedMemory`, `CameraSharedMemoryRingBuffer.put_frame` / `get_next_data`, `SharedMemoryNumber`,
`create_frame_dtype`). Reference sizes: 1280x720 and 1920x1080 BGR (plus 64x64 to isolate per-frame overhead).

Results: `results/cpp_comparison.md` (all tables, generated by `summarize.py`), raw JSON per run under `results/`.
Verdict and hypothesis-by-hypothesis table: section "Verdict" below (and `../study_state/cpp_result.json`).

## Verdict

**Porting SkellyCam's hot paths to C++ would not raise throughput enough to matter for 5 cameras at 60 fps. The gains come from
algorithm and architecture changes, and those can be made in Python with the same result.**

* **The frame data path is the same speed in both languages.** For the same algorithm the C++ ring is within 1-4% of Python.
  That holds for one copy: 0.146 vs 0.147 ms at 1080p. It also holds for the same lossless SPSC topology: 543/535 vs 527/537 fps per camera at 5x1080p.
  A literal port of today's `put_frame` is only 2-7% faster than the Python original, because the cost is in the algorithm:
  a fresh allocation and two copies ([`ring_buffer_shared_memory.py` L118-133](https://github.com/freemocap/skellycam/blob/23ccbf208e43879bfc74fc01049e5af2a623933d/skellycam/core/ipc/shared_memory/ring_buffer_shared_memory.py#L118-L133)).
  Removing that copy gives 4.4-9x, and Python gets all of it.
* **Where C++ wins:**
  - **Per-call fixed overhead**, which shows only with tiny frames. A publish costs about 0.6 us less than with lean numpy
    (0.8 vs 1.4 us), and the SPSC rate is 3.3x at 64x64. At 300 frames/s that is about 0.2 ms of CPU per second.
  - **Streaming stores for small copies**: 46.5 vs 10.8 GB/s at 12 KB, but equal at frame sizes.
  - **Per-pixel loops** that numpy expresses as strided copies: 7.7x. OpenCV called from Python closes this gap and goes beyond it.
  - **API surface**: `cv::imdecode` with a `dst` decodes straight into the slot and saves 0.95 ms per 1080p frame (8%).
    The Python binding lacks `dst`, but Python already has in-place paths: `VideoCapture.retrieve(image=slot)` and simplejpeg
    into the slot (prototypes P1, `p1_write.md`).
  - **Atomics with real memory ordering**, which are needed only off x86-64.
* **Where C++ does not win:**
  - **Bulk copies** (N1).
  - **Decode, encode and record.** They are native in both, so the OpenCV build decides the speed. On this machine Python's
    cv2 4.12 is 1.6x faster at decode and 4.9x faster at q90 encode than the C++ 4.8 SDK. A C++ port linked against a stock SDK could therefore be *slower*.
  - **Threads vs processes** (C5).
  - **Sleep and wake latency** (N7).
  - **SkellyCam's control-plane overhead**: 13.5 us per nested timestamp write and about 5 us per `SharedMemoryNumber` access.
    A cached view in Python removes 99.6% of it.
* **Does it matter for 5x60?** No:
  - **Baseline:** the current stack misses 60 fps at 5x1080p with MJPEG decode, reaching 53.6 fps (`../baseline/results/e_e2e_summary.md`).
    Each loop iteration spends about 10.1-10.3 ms in retrieve, 3.6-3.7 ms in put_frame and 1.1-1.2 ms in record_frame
    (loop: [`opencv_camera_loop.py` L67-117](https://github.com/freemocap/skellycam/blob/23ccbf208e43879bfc74fc01049e5af2a623933d/skellycam/core/camera/opencv/opencv_camera_loop.py#L67-L117)).
  - **What C++ adds to that loop** (EXTRAPOLATION from the rows above, assuming the same per-call costs inside the full loop):
    a line-by-line port saves about 0.1 ms of put_frame (3-4%). Decode, encode and record are unchanged.
  - **The Python fixes recover the rest:** put_frame drops from 2.77 to 0.64 ms at 5x1080p, and the control plane from about
    0.42 ms (31 timestamp writes x 13.5 us) to about 2 us.
  - **The prototypes already showed** that the Python-only redesign reaches 59.95 fps with 0 sensor frames lost at 5x1080p
    (`../prototypes/results/p8_e2e_summary.md`).
  - **Ring headroom:** the fixed Python ring sustains 527-537 fps per camera at 5x1080p with a lossless reader, about 9x the
    60 fps target. Even HEAD's ring sustains 243-250 fps.
* **When C++ would earn its place** (not needed for the 5x60 target):
  - A custom capture filter that removes the backend's internal copies (C1, untested).
  - Large pages (C4, blocked by privilege).
  - A non-x86 port of the seqlock.
  - Rates above several hundred thousand frames/s per process, which no camera produces.
  - The **hybrid** is cheap if it is ever wanted: a pybind11 or ctypes call into the same C++ ring matched pure C++ at
    frame sizes (0.147 vs 0.146 ms), with zero copies across the binding.

## Limitations

* **Synthetic frames only.** No real-camera run was made in this stage. A native DirectShow/MF capture path (C1) was not built.
  Prototypes P9 already measured real cameras through OpenCV.
* **Only one C++ OpenCV version.** The only C++ SDK on the machine is OpenCV 4.8.0. No C++ FFmpeg, libjpeg-turbo or OpenCV 4.12
  SDK was available, and nothing was installed system-wide. A version-matched cv2 4.8.0.76 Python venv separates language from library.
  The two 4.8.0 builds still differ (official SDK: MSVC 1928 /MD; PyPI wheel: MSVC 1900 /MT), so the 10-11% decode gap between them
  cannot be attributed to the language. Interpreter overhead per call is measured at about 0.5 us (64x64 rows), far below 1.4 ms.
* **The `py_seq` seqlock is x86-64 only.** It relies on x86-64 store ordering and 8-byte aligned numpy int64 stores. 0 torn frames
  were observed, which is evidence, not proof. The C++ ring uses `std::atomic` with acquire/release, which is portable.
* **Polling CPU is not a language comparison.** Readers and blocked writers poll with `Sleep(0)` in every implementation, so polling
  dominates paced-run CPU. An event-based wake-up was not measured.
* **Timer resolution.** The QPC tick is 100 ns, so sub-microsecond latencies (ping-pong, 64x64 copies) are quantised. The ns/op rows use throughput loops instead.
* **Encoder CPU noise.** With OpenCV's default thread pool, MSMF encoder CPU varies by about 10% between runs (1127-1279%). The C++ vs
  Python CPU difference in those rows is within that spread and is not a firm language effect.
* **Open items.** N8 (disk) and C4 (large pages) are open. The full e2e camera loop was not ported to C++; its effect is extrapolated above from component rows.
