# intra_playback: intra-only H.264 / HEVC from the hardware encoders vs the JPEG path in Chromium (G8, G9)

Machine Gerald, 2026-11-09. **Functional only: no timing numbers** (other agents were running; the three browsers also ran in parallel).
Labels: **measured** (result file), **source** (primary source), **code** (file:line), **inferred** (marked, minimal).
Paths are relative to `research/skellycam_recording/recording_upgrade/` unless they start with `C:/`.
`R` = `results/intra_playback/`, `F` = `R/functional/<e35|e45|c156>/`. Full tables: `R/functional_tables.md` (generated by `scripts/intra_playback/summarize_intra.py`).

Question: can intra-only H.264 and HEVC from `h264_nvenc`, `hevc_nvenc`, `h264_qsv` and `hevc_qsv` be played and scrubbed frame-exactly in Electron 35.7.5, Electron 45.2.3 and Chrome 156, compared with the JPEG-sequence path?

## 1. Answer

- measured: **yes, on this machine (RTX 3070 decode).** All 48 H.264/HEVC intra clips (4 encoders x 3 containers x 4 contents) open, play and seek in all three browsers.
  - Paused seeks to the middle of the frame interval from the real pts (`mid`): **4800/4800 exact per browser**.
  - WebCodecs by index, flush after each chunk: **4800/4800 per browser**.
  - Single steps (`<video>` mid and WebCodecs): **5856/5856 each, per browser**.
  - Every seek decoded exactly one chunk (`decoded_hist {"1": n}`), so **each H.264/HEVC intra frame decodes alone**.
  - Source: `F/seek_*.json` and `F/step_*.json`; totals were recomputed from the JSONs in this session.
- measured: the **JPEG path** (concatenated `.mjpeg` + index, and JPEG-in-MKV + index; Range fetch, then `createImageBitmap` or `ImageDecoder`) was exact in every run.
  - Seeks: 800/800 per path per browser.
  - Steps: 976/976 per path per browser.
  - Playback pattern check: 1200/1200 frames per browser.
- measured: **`currentTime = (k + 0.5) / fps` is exact on CFR files only**: 2400/2400 per browser.
  - On real capture timing (VFR) it gives 228/2400 per browser; misses are +1 (1128), +2 (792) and +3 (252) frames, summed over browsers.
  - VFR files need `mid` from the file's pts, which was 2400/2400 exact.
- measured: **one stream-level difference matters for WebCodecs.** `h264_nvenc` frames are not output after a single `decode()` until `flush()` is called: 360/360 seeks per browser needed the fallback flush.
  - `h264_qsv`, `hevc_nvenc` and `hevc_qsv` never needed it (0/360), and neither did the software H.264 decoder.
  - The `h264_nvenc` SPS has `bitstream_restriction_flag = 0`; `h264_qsv` writes `max_num_reorder_frames = 0` (`R/sps_vui_trace.txt`).
  - inferred: without that VUI field, the hardware decoder keeps the frame in the DPB until more data or a flush arrives.
  - Remedy, measured: call `flush()` after each key chunk (harness option `wcflush=1`). It was exact in every run.
- measured: **MJPEG in MKV does not play in `<video>`** in any of the three browsers: `DEMUXER_ERROR_NO_SUPPORTED_STREAMS`, 4 contents x 3 browsers (`F/seek_*.json`, clip `*/mjpeg_qsv422.mkv`). This confirms chromium_codecs NOTES §2.
- measured: **JPEG-in-MKV byte-range access works (G1 + G9 together).** The page fetched the cameras' own unmodified JPEG bytes out of an MKV by byte offset from a sidecar index (300 frames sequential + 150 random, per browser).
  - All 450 came back HTTP 206, **byte-identical to the corpus files**, starting with SOI and ending with EOI.
  - All 450 decoded with both `createImageBitmap` and `ImageDecoder` (`F/jpegmkv_seq.json`, `F/jpegmkv_random.json`).
- measured: **HEVC is hardware-only in all three browsers.**
  - `<video>` and WebCodecs `prefer-hardware` use `D3D11VideoDecoder`.
  - WebCodecs `prefer-software` for HEVC fails with `config not supported` in E35, E45 and C156 (`F/seek_*.json`, `F/caps.json`).
  - H.264 `prefer-software` decodes with `FFmpegVideoDecoder`.
- measured: **E35 vs E45 for HEVC Main / H.264 intra.**
  - Seek and step results are identical in E35, E45 and C156.
  - Playback differs only in the VFR `<video>` readback mismatches and rVFC callback counts (section 4.3).
  - Decoder choice is the same in all three.
  - The API probes differ only for the MKV container:
    - E35 returns `canPlayType('video/x-matroska; codecs=…') = ""` and MediaCapabilities `unsupported`;
    - E45 and C156 return `probably` / `supported, smooth, powerEfficient`;
    - all three still play the MKV files (`F/caps.json`).

## 2. Clips (PyAV 19.0.2)

Script: `scripts/intra_playback/gen_intra_clips.py`. Run with `uv run --script`, PEP 723 pins `av==19.0.2`, `numpy==2.2.6`.

- measured: generator versions: PyAV 19.0.2, libavcodec 63.1.102, libavformat 63.1.102, Python 3.12.13 (`R/clips_summary.json` `generator`).
- Source frames (code: `gen_intra_clips.py` `CONTENTS`, `Frames`):
  - corpus camera JPEGs decoded with PyAV's `mjpeg` decoder;
  - the chromium_sync_scrub 16-bit index pattern burned into the top strip (same layout as `scripts/chromium_sync_scrub/gen_clips.py`).

| content | corpus set | frames | timing |
|---|---|---|---|
| c720p30 | c930e_720p_flash (600 distinct real frames) | 600 | CFR 30 |
| c1080p30 | c922_1080p (19 real frames looped; pattern unique per frame) | 600 | CFR 30 |
| vfr720p | c930e_720p_flash, all frames | 891 | real MF capture times (incl. the 0.011 ms pair at frames 81/82) |
| vfr1080p | c922_1080p looped | 600 | first 600 real capture times |

- Encode: each encoder writes MP4 once (+faststart, time base 1/90000). The same packets are remuxed into fMP4 (`frag_keyframe+empty_moov+default_base_moof`, 1/90000) and MKV (1/1000).
  - Settings: NVENC `gop_size=0`, `rc=constqp`; QSV `gop_size=1`, ICQ `global_quality`; `max_b_frames=0`; input NV12 limited range (code: `enc_setup`, `encode_mp4`, `remux`).
- measured: in VFR MKV one pts was bumped by 1 ms to stay increasing (the 0.011 ms pair; `mux_flags.pts_adjusted_for_monotonic = 1`). MP4 keeps the pair 1 tick apart (pts 2.703978 / 2.703989 s) (`R/clips_summary.json`).
- JPEG path: `mjpeg_qsv` from YUYV (full range), giving 4:2:2 baseline JPEGs (`decoded_formats ['yuvj422p']`, 600/600 SOF0). It is written as `jpeg_qsv422/clip.mjpeg` + index and as `mjpeg_qsv422.mkv` + an index of byte offsets inside the MKV.
  - measured: the MKV sample sizes equal the `.mjpeg` sizes (`sizes_equal_jpeg_seq: true`).
  - measured: in MKV, `packet.pos` is 4 bytes before the payload for every packet (`pos_delta_hist {"4": n}`), as in chromium_sync_scrub F18.
- Camera-bytes MKV: the first 300 unmodified c930e_720p JPEGs, muxed with `add_mux_stream('mjpeg')` (`sizes_equal_corpus: true`).
- measured: **every H.264/HEVC clip is all-IDR with no B-frames**:
  - NAL scan: IDR in every frame (H.264 type 5; HEVC type 19 = IDR_W_RADL) and 0 non-IRAP VCL NAL units;
  - container key flag on every frame;
  - ffprobe 9.0.2: `key_frame` = 1 and `pict_type` I on every frame, `has_b_frames = 0`;
  - this holds for all 48 files (`R/clips_summary.json` `nal_check`, `ffprobe`).
- measured: per-packet NAL layout:
  - `h264_nvenc`: [SEI, SEI, IDR], with SPS/PPS only in avcC;
  - `h264_qsv`: [SPS, PPS, SEI, IDR];
  - `hevc_nvenc`: [SEI(39), IDR];
  - `hevc_qsv`: [VPS, SPS, PPS, SEI, IDR].
- measured: the FFmpeg MP4 muxer tags HEVC as `hev1`. The MKV tag is empty, and the page uses `hvc1.*` for it. Both work in all three browsers.
- measured: software decode-back of each MP4 read the index pattern on every frame (600 or 891 of each).
- Quality was matched by Y-PSNR. Per encoder and height, the quality parameter closest to 55.0 dB on 30 frames was chosen.
  - 55 dB is about what `mjpeg_qsv` gives at roughly the cameras' own JPEG size: c930e 720p corpus median 56,759 B/frame (`corpus/index.json`).
  - Y-PSNR is in limited-range units; full-range JPEG luma is mapped with 16 + 219*y/255. SSIM is an 8x8 box-window SSIM on Y, not identical to ffmpeg's ssim filter.
  - Whole-file values, from 1 in 10 frames (measured, `R/clips_summary.json`):

| encoder | 720p q | 720p bytes/frame | 720p Y-PSNR / SSIM | 1080p q | 1080p bytes/frame | 1080p Y-PSNR / SSIM |
|---|---|---|---|---|---|---|
| h264_nvenc (constqp) | 17 | 33,772 | 55.42 / 0.9979 | 14 | 181,957 | 54.49 / 0.9969 |
| hevc_nvenc (constqp) | 17 | 27,457 | 54.54 / 0.9973 | 11 | 213,013 | 54.92 / 0.9971 |
| h264_qsv (ICQ) | 11 | 41,340 | 55.71 / 0.9980 | 8 | 223,571 | 54.93 / 0.9972 |

- Notes on the table:
  - The sweep step is 3 QP. The points are within 1.2 dB of each other, not equal; the full sweeps are in `R/functional_tables.md` "Quality calibration".
  - The 1080p content is 19 frames looped, so the 1080p sizes are intra sizes of only 19 distinct pictures.
  - This is a playback fixture, not the matched-quality encode comparison (that is `intra_compare` / `hw_accel_target`).
- measured: nvidia-smi encoder sessions were 1 before generation (another process; Parsec/Sunshine were running per `results/hw_accel_target/NOTES_functional.md` §2) and 1–2 while NVENC was open (`R/gen_nvidia_smi_*.txt`, `nvidia_smi` per clip in `R/clips_summary.json`).

## 5. Implications (inferred unless labelled)

- For G9, intra-only H.264/HEVC behave like the JPEG path for exactness, provided the UI:
  - (a) seeks `<video>` to `mid` from the file's real pts, not (k+0.5)/fps, because real recordings are VFR (measured 4.1); or
  - (b) uses WebCodecs by index, calling `flush()` after each key chunk (measured 4.1, `h264_nvenc` case).
- For G8, both codecs play natively in E35, E45 and C156 here, but only through the hardware decoder for HEVC (measured 4.5).
  - inferred: a machine without HEVC decode hardware gets no HEVC playback at all in these Chromium builds; H.264 falls back to FFmpeg.
- For G1 + G9, an MKV of untouched camera JPEGs plus a byte-offset sidecar can drive frame-exact UI access without `<video>` (measured §1). `<video>` cannot open it (measured).
- The decode-cost side (latency per frame, N = 4/8 sync spread, scrub rate, CPU) is tonight's bench (section 7).

## 6. Not tested / limits

- Single machine, NVIDIA decode only. No Intel/AMD/Apple GPU decode, no machine without HEVC hardware, no Linux/macOS.
- HEVC 4:2:2 (`hevc_qsv` from YUYV) was not played. chromium_codecs NOTES §3 probes show E35 unsupported and E45/C156 supported for RExt 4:2:2; `results/hw_accel_target/NOTES_functional.md` §4 shows NVIDIA cannot decode it.
- The 0.011 ms VFR pair was not targeted explicitly. Random seeks cover it only by chance (chromium_sync_scrub F16a covers it for older clips).
- Short files (600–891 frames). The 1080p content is 19 real frames looped.
- Functional runs were on a shared machine, with E35, E45 and C156 in parallel. CPU samples were removed from the functional JSONs.
- The H.264 NVENC flush behaviour is explained only by the SPS field (`R/sps_vui_trace.txt`). Chromium's decoder code was not traced (inferred, NOT VERIFIED). No NVENC option to write `bitstream_restriction` was checked.
- The `<video>` playback mismatches in 4.3 are not resolved to screen content (NOT VERIFIED).
- The "plays" check covers 5 s per clip; the whole file was not played.
