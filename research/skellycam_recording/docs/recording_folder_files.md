# Recording manifest and skellycam metadata files: who defines which fields

2026-11-12. Question (Dom): should skellyfileformat's `SPEC.md` define the recording manifest fields (plan row S8, skellyfileformat ADR-83Y4), or should skellycam? And what defines the fields of every other file that skellycam writes?

*Written by a sub-agent (read-only code reading); saved by the main session. Before saving, the main session checked these claims against the code: freemocap reads `videos` from the info JSON (`video_group_helper.py:559`) and `framerate_stats.median` from the stats JSON (`recording_framerate.py:72`); upstream `main`'s `recording_info.py` writes no `videos` field and stores an absolute `recording_directory` (`:20, :34`); upstream `sfn26` adds `VideoAssociations` (`recording_info.py:10, :90`). The sub-agent ran one `git fetch --dry-run upstream` (read-only, no change).*

**Labels:** [C] code read (file:line), [I] inferred, [NV] not verified. Paths: skellycam = the `skellycam-phase1` worktree (upstream `main`); freemocap = branch `development` (it pins skellycam `branch = "main"`, `pyproject.toml:43` [C]).

## 0. Short answer
Option (b): skellycam's own spec defines the manifest. `SPEC.md` defines only what is inside the MKV/MKA files, plus the rule a reader uses to bind a sidecar to its file (the Segment UID in the sidecar header), so a reader can find and bind files without any manifest.

Today no file that skellycam writes has a schema. The only definitions are pydantic models or numpy dtypes in the writing code, plus two partial and partly wrong docs pages. No file carries a version field.

## 4. Options for the manifest
- **(a) `SPEC.md` defines the manifest fields.** For: one document and one versioning rule for an outside implementer. Against: the fields sit in a file that is mostly skellycam data (`camera_configs`, FullTimestamp, an absolute directory), so either two specs own one file or every config change becomes a format change (ADR-M4DF); skellysync writes the format but no info JSON (its SCOPE never mentions one [C]); outside the v0 scope (ADR-CD4G); duplicates the sidecar header, which already carries the stable key and the Segment UID (plan row 1.5 [C]; ADR-69YS does not list the key yet); old recordings have no manifest, and ADR-X7FT §6 keeps legacy reading out of the spec.
- **(b) skellycam defines the manifest (its recording-folder spec and the freemocap contract, D22); `SPEC.md` defines file contents and binding.** For: matches who writes the file; freemocap's read of `videos` is already a skellycam → freemocap contract; the legacy fallback (no manifest → scan the folder, parse names, read CSVs) belongs to skellycam (ADR-X7FT §6); manifest edits never bump the format version; `SPEC.md` stays self-contained, because a reader binds by the header UID alone. Against: skellycam must add a version field to the info JSON; an outside reader of a skellycam folder needs two documents; skellycam's spec must say the header UID wins over the manifest when they disagree.
- **(c) A split.** `SPEC.md` defines the binding rule (the header UID is authoritative; no external index overrides it), the UID's text encoding, and optionally a reusable JSON "file reference" object `{mkv, sidecar, key, segment_uid}` with folder-relative paths; skellycam's spec places it in the info JSON under a key skellycam owns. For: skellycam and skellysync encode it the same way. Against: more cross-references; a change to the object becomes a format change.
- **(d) A separate manifest file owned by skellyfileformat.** Clean ownership, but it duplicates the info JSON, which freemocap already reads.

## 5. Proposed rule for the wider question [I]
**The spec of the program whose code writes a file defines that file. A file is in `SPEC.md` only if more than one program must write it byte-compatibly (skellycam, skellysync, the converter), i.e. its bytes come from skellyfileformat code. A field that another program reads appears in the reader's contract spec as a reference to the owner's requirement ID, marked "meaning frozen", and is never defined twice.**

Applied:
- **`SPEC.md`:** the camera MKV profile; the video sidecar (embedded or separate); `.audio.mka` and `.skau`; the skellysync FLAC track; their file, attachment and MIME names; the Segment UID encoding and the binding rule.
- **skellycam recording-folder spec** (`skellycam/spec/`, D22): the folder layout; the info JSON including the manifest and a new version field; both CSVs (columns only added, existing meanings kept, §3.1; decide whether `sfn26`'s variable stage columns are allowed); the stats JSON; `_stats.txt` and the README as informative only.
- **skellycam legacy section, frozen and read-only** (new skellycam stops writing these): the WAV and `audio_timestamps.json`; H.264 MP4 and AVI videos; `.web.mp4`.
- **freemocap contract** (skellycam spec, §3.1), by reference: info JSON `videos` plus the new manifest; CSV columns `recording_frame_number`, `connection_frame_number`, `from_previous.framerate.hz`, `timestamp.from_recording_start.sec`; stats JSON `framerate_stats.median`; folder paths and the filename pattern; the Python APIs `RecordingInfo` path methods and `ParsedVideoFilename`.

## 6. Recommendation
(b), with the binding-rule part of (c): `SPEC.md` states that the sidecar header's Segment UID decides the binding and defines the UID's text encoding. Reasons: the info JSON is a skellycam file, and skellysync writes the format without one; the sidecar header already makes the format self-describing; legacy reading belongs to skellycam (ADR-X7FT §6); freemocap's existing read is a skellycam → freemocap contract; the format version stays tied to real format changes. skellycam's spec should also add a version field to the info JSON and decide whether to keep the absolute `recording_directory` (`recording_info.py:20`), which puts a local user path into a file that may be shared.
