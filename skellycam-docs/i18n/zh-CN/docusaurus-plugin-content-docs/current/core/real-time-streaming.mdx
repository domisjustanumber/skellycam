## Each camera on its own

The live preview sends each camera on its own. For each WebSocket connection, the server has one sender, `PreviewRelay`. In each pass, the sender reads the frame ring of each camera and sends the newest frame that it has not sent yet, as one binary camera message. It skips the older frames and keeps no queue, so a connection has at most one camera message in flight for each camera.

Each camera has its own flow control. When the UI has drawn a frame, it sends a ready message for that camera, `{"message_type": "camera_ready", "camera_id": "a1b2"}`. Then the sender can send that camera its next frame. When no ready message comes, a safety net sends the newest unsent frame of that camera one time each second. Thus a slow camera or a slow tile holds back only its own camera. The other cameras go on at their own rate.

The preview does not wait for the lockstep gate or for equal frame numbers. A camera with a new frame in its ring is shown. A camera with no new frame keeps its last frame on the screen. Thus the tiles can show frames of slightly different moments. For frame-matched data from many cameras, see [Frame-Perfect Sync](./frame-perfect-sync).

## WebSocket 协议

SkellyCam 使用紧凑的二进制 WebSocket 协议来流传输帧：

1. **Untouched JPEG** — The server sends the JPEG of the frame ring of each camera as it is: no resize, no re-encode, no rotation.
2. **One message for each camera frame** — Each binary message holds one frame of one camera, after a header of 48 bytes (version, flags, frame number, arrival time, rotation, JPEG length, camera ID).
3. **Flow control for each camera** — The server sends a camera its next frame when the client has drawn the last one, and drops the frames in between. With no ready message, a safety net sends one frame each second. A slow camera or a slow tile holds back only its own camera.

同一 WebSocket 连接还承载日志、状态更新、帧率统计和控制命令的 JSON 消息。

完整协议详情请参见 [WebSocket 协议](../technical/websocket-protocol)参考。

## 前端渲染

React/Electron 前端通过优化性能的管道处理传入的帧：

1. **Parse** — `parseCameraMessage` reads the header and gives a view of the JPEG bytes, with no copy.
2. **Newest pending** — `PreviewTiles` keeps only the newest message of each camera and gives each tile one update at a time, at most one for each display refresh.
3. **Decode and draw** — The shared tile of the player decodes the JPEG with `ImageDecoder` and draws it with its overlay on the main thread. Then the UI sends one ready message for that camera.

此架构支持多个同时的摄像头画面而不会在 UI 中丢帧。

## 未来计划

当前实现使用基于 TCP 的 WebSocket，可靠但 TCP 的排序保证增加了延迟。对于高吞吐量的局域网场景，UDP 传输可以通过在传输层而非应用层允许丢帧来减少延迟。请参见上方的路线图项目了解计划中的传输和客户端改进。
