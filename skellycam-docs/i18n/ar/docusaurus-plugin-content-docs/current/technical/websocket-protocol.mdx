# بروتوكول WebSocket

تحمل نقطة نهاية WebSocket على `/skellycam/websocket/connect` ثلاثة أنواع من حركة البيانات:

1. **Binary camera messages** (server -> client): one JPEG frame of one camera in each message
2. **JSON messages** (server -> client): log records, framerate updates, application state
3. **Text messages** (client -> server): ready messages and ping/pong

## دورة حياة الاتصال

1. يفتح العميل اتصال WebSocket على `/skellycam/websocket/connect`.
2. يقبل الخادم الاتصال ويبدأ أربع مهام متزامنة: ترحيل الصور، ترحيل السجلات، مرسل الحالة، ومعالج رسائل العميل.
3. يبدأ العميل في استقبال الرسائل فورًا.
4. عندما ينقطع العميل (أو يُغلق الخادم)، تُلغى جميع المهام ويُغلق الاتصال.

## Binary Camera Message Format

When cameras are active, the server sends one binary message for each frame of each camera that it sends: the
camera message. It is a header of 48 bytes, then the JPEG bytes of the frame ring, untouched (no resize, no
re-encode, no rotation). Each camera has its own messages, so a slow or a stopped camera does not hold back another
camera.

```
+--------------------------------------------+
|           Header (48 bytes)                |
+--------------------------------------------+
|           JPEG (jpeg_len bytes)            |
+--------------------------------------------+
```

All multi-byte integers are **little-endian**. The Python form is `struct.Struct("<B3xIqqII16s")`. The message length
is `48 + jpeg_len`.

| Offset | Size | Type | Name | Value |
|---|---|---|---|---|
| 0 | 1 | u8 | `version` | 1. It is also the message type. |
| 1 | 3 | | reserved | zero |
| 4 | 4 | u32 | `flags` | the ring flags, all 32 bits |
| 8 | 8 | i64 | `frame_number` | the frame number of the camera |
| 16 | 8 | i64 | `arrival_ns` | `perf_counter_ns` at the capture callback |
| 24 | 4 | u32 | `rotation_cw_deg` | 0, 90, 180 or 270 |
| 28 | 4 | u32 | `jpeg_len` | the number of JPEG bytes after the header; 0 for a flagged frame |
| 32 | 16 | ASCII | `camera_id` | the camera id, NUL-padded |
| 48 | `jpeg_len` | bytes | JPEG | the bytes of the ring, untouched |

Example: camera `a1b2`, frame 258, arrival 1,000,000,007 ns, rotation 90, flags 0x30, and the 4 bytes `FF D8 FF D9`
as the JPEG:

```text
 0: 01 00 00 00 30 00 00 00 02 01 00 00 00 00 00 00
16: 07 ca 9a 3b 00 00 00 00 5a 00 00 00 04 00 00 00
32: 61 31 62 32 00 00 00 00 00 00 00 00 00 00 00 00
48: ff d8 ff d9
```

### Field Rules

- **`version`**: a parser that sees a value other than 1 refuses the message and logs both values.
- **`frame_number`** and **`arrival_ns`** are 64-bit values. A JavaScript client reads them as `BigInt`
  (`DataView.getBigInt64`).
- **A flagged frame**: when `flags & 0x0F` is not zero, the message has no JPEG (`jpeg_len` 0). The client keeps the
  last image and shows the mark "flagged frame".
- A client refuses a message that is shorter than 48 bytes, whose length is not `48 + jpeg_len`, whose rotation is
  not one of the four values, or whose camera id is empty.

### Implementation References

- **Python (server):** `skellycam/api/websocket/preview_relay.py`: `pack_camera_frame()` builds the message, and
  `PreviewRelay` sends the messages of one connection. `skellycam/api/websocket/websocket_message_types.py`:
  `WebsocketMessageType` defines the JSON message type strings.
- **TypeScript (client):** `skellycam-ui/src/services/server/preview/camera-message.ts`: `parseCameraMessage()`.
  `preview-tiles.ts`: `PreviewTiles`, the flow control for each camera. The shared tile of
  `skellycam-ui/src/player/` decodes the JPEG with `ImageDecoder` and draws it on the main thread.

## رسائل JSON (خادم -> عميل)

### سجلات

```json
{
  "message_type": "log_record",
  "levelname": "INFO",
  "levelno": 20,
  "message": "Camera group started",
  "name": "skellycam.core.camera_group",
  "filename": "camera_group.py",
  "lineno": 42,
  "funcName": "start",
  "created": 1700000000.123,
  "formatted_message": "2024-01-01 12:00:00 [INFO] Camera group started",
  "delta_t": "0.123ms"
}
```

يتم توجيه سجلات بمستوى `TRACE` (المستوى 5) وأعلى إلى WebSocket. تعرض الواجهة الأمامية هذه السجلات في لوحة الطرفية. يتم إنتاج السجلات بواسطة [skellylogs](https://github.com/freemocap/skellylogs).

### Framerate Updates

```json
{
  "message_type": "framerate_update",
  "camera_group_id": "group-0",
  "cameras": {
    "a1b2": {
      "delivered_framerate": {
        "mean_frame_duration_ms": 33.3,
        "mean_frames_per_second": 30.0,
        "frame_duration_max": 40.1,
        "frame_duration_min": 28.5,
        "frame_duration_mean": 33.3,
        "frame_duration_stddev": 2.1,
        "frame_duration_median": 33.2,
        "frame_duration_coefficient_of_variation": 0.063,
        "calculation_window_size": 8,
        "framerate_source": "a1b2"
      },
      "not_shown_count": 3,
      "ring_skipped_count": 0,
      "oversize_count": 0
    }
  }
}
```

Sent every 250 ms for each group, with one item for each camera. The values are for this connection:

- `delivered_framerate`: the rate at which the camera delivered frames to the server, from the frame numbers and the
  capture times of the frame ring. It does not depend on the client. `null` when there is not enough data. The UI
  shows it as "Captured".
- `not_shown_count`: the frames that the server did not send on this connection, because the client was slower than
  the camera.
- `ring_skipped_count`: the frames that the frame ring skipped.
- `oversize_count`: the frames that were larger than their ring slot.

The UI computes "Displayed" itself: the frames that its window drew for each camera. `replaced_count` (the frames
that the gate replaced) is in the camera status of `app_state`, at
`state.camera_groups[<group id>].cameras[<camera id>].status`, with the camera `state`.

### حالة التطبيق

```json
{
  "message_type": "app_state",
  "state": {
    "camera_groups": {
      "group-0": {
        "id": "group-0",
        "camera_ids": ["0", "1"],
        "is_recording": false,
        "is_paused": false
      }
    }
  }
}
```

تُرسل تقريبًا كل ثانية وعند كل تغيير في حالة التطبيق (مثل بدء/إيقاف التسجيل).

## Client -> Server Messages

### Ready Message

When the client has drawn the frame of a camera message, it sends one ready message for that camera:

```json
{"message_type": "camera_ready", "camera_id": "a1b2"}
```

### Ping/Pong

Sending the text `"ping"` will receive `"pong"` in response. This can be used for connection health checks.

## Flow Control and the Safety Net

The server sends a camera at most one camera message that is not yet ready:

1. After a camera message, the server waits for the ready message of that camera. Then it sends the newest frame of
   that camera. The frames in between are not shown, and `not_shown_count` counts them.
2. The client keeps only the newest pending message of each camera, gives the tile one update at a time, and draws at
   most one frame of each camera for each display refresh. It sends one ready message for each draw.
3. **The safety net**: when no ready message comes, the server sends the newest frame of the camera after 1 s all
   the same. A hidden window thus gets one message each second for each camera.

A slow camera or a slow tile holds back only its own camera. Websocket compression is off: a client must not need it.
